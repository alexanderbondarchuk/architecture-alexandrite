# Анализ, идентификация проблем и поиск решений

## Потенциальные проблемные места

1. MES - самое проблемное место в архитектуре
    - Отвечает за расчёт стоимости заказа. Время расчёта зависит от сложности 3Д-модели в текущий момент варируется от 2 до 30 минут (зависит от количества полигонов)
    - Ежемесячно количество заказов линейно прирастает на 100шт. Даже при стабильно работающей архитектуре в целом, время расчёта стоимости заказа будет линейно расти

2. Отсутствуют механизмы масштабирование. Все сервисы и базы развёрнуты в одном экземпляре
    - При росте нагрузки возможен отказ любого звена
    - Нет реплик баз данных

3. Временные издержки на проведение ручного тестирования и задержка поставок новых версий
    - Отсутствуют автоматизированные тесты
    - Зависимость релиза от результатов проверки единственным QA-инженером

4. Временные издержки на развёртывание вручную на стендах release и production
    - Отсутствует автоматизация развёртывания протестированных сборок

5. Долгая загрузка первой страницы MES у операторов
    - Пагинация и фильтры не помогли, значит может требоваться оптимизация sql-запросов и конфигурации базы данных
    - Отсутствует сервис кеширования

6. Очередь сообщений
    - Имеются жалобы о неполучении заказов, что может означать потерю сообщений в очереди
    - Отсутствует приоретизация очереди, например по стоимости заказа

7. Наблюдаемость (Observability)
    - Отсутствуют инструменты мониторинга, логирования и трессировки

8. Компетенция участников команды
    - Только один участник команды частично знает React
    - QA-инженер единовременно может проверять один сервис

## Инициативы для устранения нежелательных ситуаций (в порядке приоритета)

1. Автоматировать тест-кейсы
    - Автоматизация тест-кейсов позволить ускорить процесс регрессионного тестирования
    - Найм дополнительного QA-инженера для ускорения разработки автоматизированных тестов и ускорения кейсов требующих ручной проверки
2. Вынести механизм расчёта стоимости заказа в отдельный сервис и развернуть его в нескольких экземплярах
    - В процессе выделения расчёта в отдельный сервис могут быть оптимизирвованы механизмы расчёта и развёрнуто несколько экземпляров сервиса для временного нивелирования проблемы с задержкой заказов эмперическим методом
    - Возможно, ускорит работу первой страницы MES, т.к. нагрузка снизится
3. Внедрить инструменты наблюдаемости (observability)
    - Текущее архитектурное решение не позволяет мониторить метрики, собирать логи и проводить трассировку запросов. Наличие таких процессов позволит проводить анализ узких мест системы, выявит точки простоя и агрегирует сообщения об ошибках
4. Автоматизировать деплой на release и production стенды
    - Ускорит доставку протестированных новых функций и правок в production
5. Масштабировать базы данных
    - В целях повышения отказоустойчивости, резервирования хранилища и прокускной способности
6. Настроить механизмы автомасштабирования сервисов
    - Для автоматического распределения при росте нагрузки и освобождения ресурсов при отсутствии нагрузки
7. Внедрить сервис кеширования
    - Для снижения нагрузки на базы данных
8. Переработать API для продавцов
    - API не должно взаимодействовать с MES и её базой напрямую. Заказы через API должны поступать в собственную базу данных и обрабатываться в порядке очереди и приоритета брокером сообщений
9. Выделить для CRM отдельную базу данных
    - Отдельная база данных для сервиса позволит лучше соответствовать практике микросервисного подхода вместе с чем позволит отдельно масштабировать и развивать модуль CRM
10. Внедрить паттерн Backpressure для управления нагрузкой на очередь
    - Большой поток заказов и их медленная обработка может переполнить оперативную память брокера сообщений, что приведёт к его нестабильной работе и потере сообщений

## Целевая архитектура через полгода

- APISIX Gateway с функционалом балансировки нагрузки перед Shop API, CRM API, MES API
- Cервисы MES, MES API, Shop, Shop API, CRM, CRM API запущены в нескольких экземплярах и зарегистрированы в Service Discovery Consul
- Новый отдельный сервис расчёта стоимости заказов, так же в нескольких экземплярах и зарегистрированный в Service Discovery
- Кластеризированные базы данных в режиме master-master
- Сервис кеширования на базе Redis
- Observability инструментарий (Grafana, Prometheus, Jaeger, Graylog, Fluentbit, OpenSearch)
