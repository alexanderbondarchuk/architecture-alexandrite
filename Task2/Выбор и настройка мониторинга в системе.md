# План по внедрению мониторинга для системы "Александрит"

## Мотивация

На текущий момент компания столкнулась со множеством ситуаций технического характера негативно влияющих на бизнес. Отсутствие возможности идентифицировать и анализировать проблемы не даёт эффективно формулировать требования для внесения правок для стабилизации работы системы. Объективные результаты мониторинга позволяют более адресно решать проблемы, а не на основе догадок. Наличие мониторинга поможет более чётко выставлять приоритеты в бизнес-развитии сервиса.

В качестве системы мониторинга используется Яндекс.Метрика, но данного инструмента не достаточно для более глубокого анализа имеющихся проблем:

- Долгий расчёт заказов в MES
- Добгая загрузка главной страницы со списком заказов в MES
- Потери и сильные задержки заказов

Внедрение мониторинга позволит не только оперативно решать технические проблемы, но и положительно повлиять на клиентский опыт, что в перспективе может повлиять на возврат клиентов для повторного заказа.

## Выбор подхода к мониторингу

Выберите, какой подход к мониторингу вы будете использовать: RED, USE или «Четыре золотых сигнала». Для разных частей системы можно использовать разные подходы.

Для распределённой системы такой как "Александрит", рекомендуется сочетать разные методики:

- **Четыре золотых сигнала** - для комплексного мониторинга веб-приложений и систем, с которыми пользователи взаимодействуют напрямую (Shop, CRM, MES).
Позволит следить за кодами ответа, временем , количеством запросов и нагруженностью системы.
- **RED** - для мониторинга скорости ответа и количества ошибок (Rabbit MQ)
Позволит отслеживать скорость обработки сообщений, ошибок "dead-letter" и накопление сообщений в ожидании.
- **USE** - для мониторинга серверов, виртуальных машин и сетевого оборудования на уровне инстансов и баз данных всей инфраструктуры "Александрит".

## Метрики

Все перечисленные метрики обязательны для мониторинга и позволят своевременно предупреждать и реагировать возможные проблемы (ошибки в работе приложений, утилизация ресурсов, нехватка места на дисках и т.д.), а так же выявлять аномалии в поведении системы "Александрит".

### Rabbit MQ

#### Number of dead-letter-exchange letters

**Dead Letter Exchange** — это механизм RabbitMQ, используемый для обработки сообщений, которые невозможно доставить обычным способом. Метрика позволит отслеживать сообщения отклонённые потребителем (ошибка обработки) и достижения очереди максимума - это поведение, как возможное, было выявлено в процессе анализа проблем текущего решения.

Лейблы: `queueName`

#### Number of message in flight

Метрика помогает оценить нагрузку на систему обмена сообщениями и эффективность взаимодействия клиентов с очередями. Высокое значение этой метрики может, среди прочих, может указывать на медленную обработку сообщений клиентом MES, а так же возможные проблемы с сетью.

Лейблы: `env`, `queueName`

### Базы данных

#### Size of db instance

Метрика позволит отслеживать динамику изменения размера базы данных и своевременно расширять ресурс или проводить мероприятия по его оптимизации.

Лейблы: `env`, `instanceId`, `dbName`

#### Memory Utilisation for db instance

Метрика позволит отслеживать использование RAM для обслуживания запросов к базам данных.

Лейблы: `env`, `instanceId`, `dbName`

#### Number of connections for db instance

Метрика позволит отслеживать количество подключений к базе данных, динамику количества во времени и принятия решения в случае превышения лимита подключений.

Лейблы: `env`, `instanceId`, `dbName`

### S3 (Simple Storage Service)

#### Size of storage

Метрика позволит отслеживать динамику изменения размера базы данных и своевременно расширять ресурс или проводить мероприятия по его оптимизации.

Лейблы: `env`, `instanceId`

### HTTP-сервисы Shop API, CRM API, MES API

#### Number of HTTP 200 и HTTP 500

Метрика позволит остлеживать количество успешных вызовов и вызовов с ошибками, а так же их соотношение. Дополнительный лейбл `userId` позволит ранжировать количество запросов по пользователю для выявления аномалий.

Лейблы: `env`, `serviceName`, `endpoint`, `userId`

#### Number of requests (RPS)

Метрика позволит отслеживать количество запросов в секунду и динамику этого показателя во времени.

Лейблы: `env`, `serviceName`, `endpoint`, `userId`

#### Response time (latency)

Метрика позволит отслеживать время ответа на запрос и выявлять наиболее медленные точки системы

Лейблы: `env`, `serviceName`, `endpoint`, `userId`

#### Number of simultanious sessions

#### CPU %

Метрика позволит отслеживать утилизацию ресурса CPU на инстансе

Лейблы: `env`, `instanceId`

#### Memory Utilisation

Метрика позволит отслеживать утилизацию ресурса RAM на инстансе

Лейблы: `env`, `instanceId`

## План действий

1. Выбрать технологический стек для мониторинга

   - Grafana для отображения метрик
   - VictoriaMetrics для сбора метрик, долгосрочного хранения, транспорта и уведомлений

2. Настроить сбор метрик и агрегацию

   - В качестве хранилища используется VictoriaMetrics
   - Подключить инстансы и сервисы к передаче метрик

3. Настроить дашборды и механизм уведомлений

   - Настроить дашборды в Grafana для отображения [метрик](#метрики)
   - Настроить критические пороги и уведомления

4. Обучение

   - Обучить команду как использовать и сопровождать технологический стек для мониторинга
   - Объяснить какие есть дашборды и для чего они нужны
   - Объяснить где смотреть логи
   - Дать инструкции по реагированию на инциденты
