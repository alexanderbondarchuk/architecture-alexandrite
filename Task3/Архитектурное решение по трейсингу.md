# Архитектурное решение по трейсингу

## Мотивация

Внедрение трейсинга позволит изучать полный путь заказа от точки его создания до точки возникновения проблемы минимизировав при этом ручной сбор и маппинг логов. Как следствие, будет установлена проблема пропажи и задержки заказов.

### Улучшаемые бизнес-метрики

1. Сокращение просроченных заказов
2. Увеличение исполненных заказов и дохода организации
3. Улучшение клиентского опыта

### Улучшаемые технические-метрики

1. Время обработки запроса
2. Сокращение количество ошибок
3. Оптимизация инфраструктуры и ресурсов после установления и устранения причин возникающих проблем

## Анализ

### Точки старта процесса

Новый заказ может поступать онлайн от покупателей через Internet Shop и от других продавцов через MES API

- Internet Shop с помощью Shop API сохраняет артефакты заказа в Shop DB и S3
- MES с помощью MES API сохраняет артефакты заказа в MES DB и S3

В процессе жизненного цикла заказа его статус и состояние управляются с помощью различных компонентов распределённой информационной системы "Александрит"

### Точки, где заказ может зависнуть или сломаться

- Нарушение целостности данных при взаимодействии MES и MES API
- Нарушение целостности и согласованности данных при выполнении распределённой транзакции сохранения данных в Rabbit MQ, MES DB и S3
- Нарушение целостности данных при взаимодействии Internet Shop и Shop API
- Нарушение целостности и согласованности данных при выполнении распределённой транзакции сохранения данных в Shop DB и S3
- Нарушение целостности и согласованности данных при взаимодействии CRM API с Rabbit MQ, Shop DB и S3
- Нарушение целостности данных при взаимодействии CRM с CRM API

### Данные необходимые для трейсинга

#### Обязательные параметры сообщений трейсинга

- `traceId` - уникальный идентификатор для всего пути заказа
- `spanId` - идентификатор подзапроса
- `created` - время создания записи
- `serviceName` - наименование сервиса, создавшего запись
- `orderId` - id заказа
- `orderStatus` - статус заказа на момент записи

#### Данные для сбора

- Заказ принят, присвоен Id
- Изменение статуса заказа
- Ошибки, в случае возникновения
- Размер и количество загружаемых файлов
- Время начала и завершения операции
- Идентификатор текущего эндпоинта
- Другие параметры вызова и контекст, которые могут помочь более точно визуализировать порядок вызовов

## Предлагаемое решение

### Инструменты

- OpenTelemetry (OTel) - стандарт для сбора, обработки и экспорта телеметрии. В качестве инструментов будут использоваться OpenTelemetry SDK и OpenTelemetry Collector.
- Jaeger - система для распределённого трейсинга, отслеживания запросов в микросервисных архитектурах.

### Реализация

1. Добавить OpenTelemetry SDK в Shop API, MES API, CRM API для трассировки запросов в БД
   - При получении входящих запросов считывать `traceId` из заголовков
   - При формировании исходящих запросов, в том числе и сообщений в RabbitMQ, подкладывать в заголовки параметр `traceId`
2. Добавить OpenTelemetry Collector
   - Агрегирует данные из множества источников
   - Буфферизирует и временно сохраняет данные, на случай если Jaeger не доступен
   - Фильтует ненужные span
   - Донасыщает сообщения дополнительными метками, например `env`
3. Добавить Jaeger
   - Подключить OpenTelemetry Collector к Jaeger
   - Настроить период хранения данных 14 дней

## Компромиссы

1. Существенные трудозатраты на внедрение, которые могут потребоваться при рефакторинге кода для адаптации под использование OpenTelemetry SDK
2. В случае с проприетарными системами (RabbitMQ, S3, MES) может потребовать сверх дополнительных трудозатрат на внедрение или закупку готовых модулей телеметрии
3. Возможны точки, где OpenTelemetry не доступен для интеграции. Тогда потребуется реализация обходного решения в виде sidecar (proxy + OpenTelemetryCollector), что так же увеличит задержки на обработку вызовов
4. Возрастает общая награзка на инфраструктуру. Используются ресурсы сети, дисков и вычислительные ресурсы серверов
5. Вопросы безопасности и внедрение механизмов аудита доступа

## Аспекты безопасности

1. Использование системы аутентификации и авторизации для доступа к Jaeger и данным трасировки
2. Срочность хранения информации содерджащей персональные и другие чувствительыне данные
3. Обезличивание и маскирование данных, требующих более длительного хранения
4. Описание и внедрение политик доступа к инструментам и данным трассировки, внедрение ролевой модели
5. Аудит доступа к системе
