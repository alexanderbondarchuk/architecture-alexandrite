# Архитектурное решение по логированию

## Мотивация

На текущий момент разбор инцидентов осуществляется по обратной связи пользователей и клиентов. Восстановление событий таким образом затрудняет разбор проблем и влияет на скорость их устранения. Ошибки и длительный разбор инцидентов влияет на клиентский опыт и доходность бизнеса.

### Централизованное логирование позволит

- Собирать логи в единой системе, что снизит нагрузку на группу поддержки и даст возможность поиска и анализа информации в единой точке хранения вместо ручного сбора по различным сервисам
- Фиксировать ошибки
- Фиксировать отклонения от заложенных/прогнозируемых показателей работы системы
- Фиксировать исполнение ключевых шагов бизнес-процессов
- Ускорить разбор инцидентов и обращений по техническим проблемам

### Влияние на бизнес

- Сокращение потерь заказов
- Увеличение скорости обработки заказов
- Возврат клиентов
- Улучшение репутации фирмы

### Метрики, на которые прямо или косвенно повлияет внедрение логирования и трейсинга

- Время доступности сервиса (Uptime / SLA)
- Среднее время устранения инцидента (MTTR – Mean Time To Repair)
- Среднее время между отказами (MTBF – Mean Time Between Failures)
- Время загрузки страницы (Page Load Time)
- Пропускная способность (Throughput)
- Коэффициент ошибок (Error Rate)
- Коэффициент конверсии (Conversion Rate)
- Процент брака/возвратов (Defect Rate)
- затраты на облачную инфраструктуру (Cloud Costs)
- Эффективность использования энергии (PUE – Power Usage Effectiveness)

## Приоритет внедрения логирования и трейсинга

Команда не сможет реализовать единовременно логирование и трейсинг всех элементов инфраструктуры.
Далее перечислены системы в порядке приоритета, где внедрение логирования даст наибольший ожидаемый эффект.

1. **MES** - ключевой узел информационной системы. По результатам проведённой аналитики именно в этой системе находятся наиболее критичные проблемы
2. **RabbitMQ** - проблемы с очередями заказов могут возникать в том числе и со стороны очереди
3. **CRM** и **Internet Shop** - узлы с меньшим количеством замечаний, но так же требующие культуры observability

## Уровни логирования

Для записи логов будут использоваться уровни определённые в RFC 5424.

`FATAL` - критическая ошибка, приводящая к остановке системы. Требует немедленного вмешательства. **Примеры:** *сервер упал, база данных недоступна, потеря критичных данных.*

`ERROR` - серьёзная ошибка, но система может продолжать работу (частичная деградация). **Примеры:** *не удалось обработать платеж, API вернул 500 ошибку, сбой в цепочке поставок.*

`WARN` - потенциальная проблема, которая пока не влияет на работу, но может стать ошибкой. **Примеры:** *медленный запрос к БД, недостаточно места на диске, подозрительная активность.*

`INFO` - стандартные события работы системы (успешные операции). Для мониторинга бизнес-процессов. **Примеры:** *пользователь зарегистрировался, заказ оплачен, отправлено уведомление.*

`DEBUG` - детальная техническая информация для разработчиков (по умолчанию отключена для production). **Примеры:** *запросы к API, значения переменных, промежуточные состояния.*

`TRACE` - максимально подробные логи (по умолчанию отключена для production). Для глубокой отладки. **Примеры:** *анализ сложных багов, performance-проблем.*

## Предлагаемое решение

### Технологии и реализация

1. Везде, где будет возможно и оправдано затратами ресурсов логи будут писаться в структурированном формате JSON в stdout или файл
2. Fluentbit будет выступать в качестве коллектора данных в централизованный сервис сбора логов
3. Для централизованного сбора логов, поиска и анализа будет использоваться Graylog
   - open-source решение, с возможностью приобретения enterprise-версии с дополнительным набором функций
   - более лёгкий в настройке, чем ELK Stack и более функциональный, чем Grafana Loki
   - интуитивный интерфейс, который проще чем Elasticsearch и Kibana
   - поддерживает большое количество источников
   - из минусов - ресурсоёмкий при больших нагрузках
4. В качестве хранилища логов будет использоваться Opensearch
5. Аналитика и визуализация Grafana
6. Алёртинг Graylog или Grafana

### Безопасность

- Доступ к логам будут иметь сотрудники прошедшие авторизацию и относящиеся к одной из категорий: поддержка, DevOps, разработчики
- Персональные данные маскируются с перспективой перехода к обезличиванию (с возможностью восстановления исходных данных для уполномоченных лиц на основе Access Control)
- Пароли и платёжная информация маскируются
- Шифрование логов в процессе передачи с помощью TLS

### Хранение

- Отдельные индексы с логами под каждый сервис и env
- Срок:
  - 14 дней INFO
  - 28 дней WARN, ERROR, FATAL
  - В случае необходимости хранить логи дольше и обеспечения условий к хранению персональной и чувстительной информации - можно архивировать и выносить логи в холодное хранилище
- Ротация:
  - Каждый день новый индекс
  - При достижении 16ГБ создаётся новый индекс

## Мероприятия для превращения системы сбора логов в систему анализа логов

1. Сохранять в логах `traceId` для удобства фильтрации данных и бесшовного перехода между логированием и трассировкой
2. Алёртинг
   - Сообщения уровня `FATAL` и `ERROR`
   - Растущее количество сообщений уровня `WARN`
   - Динамично растущее время ответа от сервисов
   - Отсутствие изменений в очереди RabbitMQ
3. Аномалии
   - Резкий рост количества ошибок авторизации
   - Резкий рост количества заказов
   - Резкий рост активности отдельного ползователя
