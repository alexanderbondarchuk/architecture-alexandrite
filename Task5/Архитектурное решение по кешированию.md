# Архитектурное решение по кешированию

## Мотивация

В MES долго загружается главная страница со списком заказов с их статусом. Пока не установлена точная причина проблемы долгой загрузки - данные для этой страницы можно кешировать. Это повысит отклик системы, а так же снизит нагрузку на базу данных MES. Кеширование демонстрирует наибольшую эффективность на редко изменяющихся данных, что подходит для сущности "Заказ".

Информацию о состоянии заказа можно кешировать и для сервисов Shop API и CRM API. Это снизит нагрузку на общую используемую базу данных Shop Db.

Так же снизить нагрузку на БД Shop Db и повысить отклик сервисов позволит кеширование информации о товарах и ценах для Shop API.

При исползовании серверного кеширования снизится нагрузка и при межсервисном взаимодействии.

## Предлагаемое решение

- Использовать серверное кеширование с помощью Redis
- Паттерн кеширования Cache-Aside
   1. При запросе на чтение идёт обращение к кешу
      - Если данных в кеше нет, то идёт обращение к базе данных, после чего результат записывается в кеш
      - Результат из кеша возвращается
   2. При запросе на запись (создание/изменение) идёт обращение к БД
      - В случае успеха записи в БД данные из кеша удаляются и замещаются обновлёнными

Паттерн **Cache-Aside** подходит по причинам:

- Простота реализации
- Отсутствие жёстких требований к согласованности и рисков из-за временной несогласованности данных
- Высокая производительность по сравнению с альтернативными способами
- Отсуствие лишних обновлений данных кеша

### Причина выбора Cache Aside вместо других альтернатив

- **Write-Through** - паттерн предполагает, что чтение и запись в базу данных будет осуществляться через кеш. Но в текущем решении уже есть проблемы с производительностью и потерей данных, а добавление новой точки отказа может усугубить ситуацию. Однако внедрение данного паттерна кеширования можно рассмотреть на следующих этапах развития системы после стабилизации её работы
- **Refresh-Ahead** - сложный в реализации паттерн, т.к. требует подбора TTL, есть риск обновления неиспользуемых данных (что повысит нагрузку на БД уже имеющую проблемы с производительностью). Процесс инвалидации данных инвалидации данных может быть реализован аналогично Cache-Aside

### Стратегия инвалидации кеша

Инвалидация данных кеша будет осуществляться с помощью следующийх стратегий:

- ***Инвалидация по ключу*** - предметная область, для которой реализована система требует достаточной степени актуальности данных и возможности управлять актуальностью. Инвалидация данных по ключу позволяет удалять данные из кеша в различных сценариях работы приложения, осносной из которых - изменение данных и статуса заказа
- ***Временная инвалидация (TTL)*** - в рамках информационной системы будет необходим больше для целей периодической очистки памяти от неиспользуемых данных кеша

Стратегия ***программной инвалидации на основе событий pub/sub*** на текущем этапе развития проекта не подойдёт, т.к. потребует внедрения дополнительных модулей и инструментов для обеспечения актуальности данных кеша. Однако, несмотря на сложность реализации, при стабилизации работы информационной системы, возможность использования этой стратегии может быть пересмотрено. Данная стратегия отличается высокой скоростью обновления данных в кеше, так как данные инвалидируются сразу после изменений в БД.
